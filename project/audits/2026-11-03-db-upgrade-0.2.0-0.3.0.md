# Audit BDD — passage de 0.2.0 à 0.3.0

Date : 2026-11-03. Périmètre : schémas déclaratifs et conversions de données des
tags publiés, puis corrections locales destinées à préparer 0.3.1. Aucun accès
à une installation extérieure ni aucune donnée de production.

## Méthode et garanties

Les modèles ont été chargés dans deux images construites avec le code et le
lockfile propres à chaque tag : `757dcdb8` pour 0.2.0, `e7f2ccc4` pour 0.3.0.
Les exports SQLAlchemy comprennent colonnes, types, défauts serveur, nullabilité,
clés étrangères, contraintes et index, ainsi que le registre des actions DbAdmin.
Les fichiers détaillés sont produits dans `artifacts/db-upgrade-audit/` :
`schema-diff.json`, `schema.patch`, `action-diff.json` et les exports par version.
Ce patch compare les cibles déclaratives ; ce n'est pas un script à appliquer.

Les vérifications PostgreSQL reconstruisent le schéma 0.2.0 exporté, avec des
données entièrement synthétiques. Les migrations utilisent le vrai orchestrateur
et le véritable exécutable Atlas. Les garanties recherchées sont la conservation
du contenu et des droits, la reprise idempotente après interruption, l'absence
de contraction prématurée et le maintien des écritures lorsque le schéma reste
temporairement utilisable avec des colonnes anciennes.

## Diff structurel

Le nombre de tables passe de **180 à 182**, celui des colonnes de **2267 à 2282**.
Il existe **5 tables ajoutées, 3 retirées et 18 tables communes modifiées**.
Dans ces tables communes : **28 colonnes ajoutées, 25 retirées et 10 définitions
de colonnes modifiées**. Neuf de ces dernières redirigent des FK de `datasets`
vers `documents` ; la dernière change le défaut de `documents.document_type`.
Les six déclarations d'ENUM PostgreSQL ne changent pas entre les deux tags.
Les tables communes perdent cinq index et en gagnent cinq ; les définitions
détaillées figurent dans le diff SQL et le diff JSON.

| Ensemble | Changement | Garantie ou mécanisme |
|---|---|---|
| `agents` | Retrait de 18 colonnes historiques : groupe, format/source, identité initiale, compteur d'avatar et configuration Hermes | Transfert vers `agent_teams`, HTML, paramètre d'identité et `hermes_agent_configs` ; tombes incluses |
| `documents` | 8 ajouts, 2 retraits, type par défaut `html` → `text` | Texte/Données canoniques, stockage typé, description courante |
| `document_revisions` | 4 ajouts, retrait des mots-clés historiques | Révisions de contenu et rétention des fichiers |
| `document_summary_revisions` | Table retirée | Archive durable vérifiée dans `galaris_migration` avant contraction |
| `document_tags` | Retrait de 3 marqueurs de classement automatique | Dossiers personnels conservés ; ancien classement automatique arrêté |
| `document_list_positions` | Ajout de `at_root` | Défaut serveur `false` |
| `datasets` | 4 champs de description courante ajoutés | Anciennes sources conservées ; transfert vers Documents |
| 7 tables auxiliaires Dataset et 2 tables d'applications documentaires | FK `dataset_id` redirigées vers `documents.id` | Références existantes conservées jusqu'au transfert ; modification des FK différée à la contraction |
| `dataset_appearances` | Ajout de `at_root` en plus de la FK | Placement personnel conservé |
| `goals` | Description documentaire remplacée par une colonne HTML | Copie du contenu courant ; suivi, historique, droits et classement du suivi conservés |
| `skills` | 8 champs de fonctionnement/apprentissage ajoutés | Procédures personnelles et activation par agent |
| `learned_skills`, `learned_skill_evidences` | Tables retirées | Transfert vers packages personnels, fichiers et `skill_learning_evidences` |
| `runtime_action_permissions` | Ajout de `allowed` | Défaut `true`, cohérent avec les anciens accords positifs |
| Nouvelles tables | `contact_discovery_jobs`, `dataset_search_indexes`, `dataset_search_chunks`, `file_derivatives`, `skill_learning_evidences` | Création additive ; index de recherche dérivés ou nouveaux états métier |

Le registre ajoute neuf actions de migration et n'en retire aucune. Deux actions
changent de checksum : conversion des profils Agent et séparation documentaire.
Dans les deux cas, 0.3.0 déclare explicitement la compatibilité avec le checksum
0.2.0. Cela autorise la reprise vers l'avant, pas l'exécution de l'ancien binaire
sur une base partiellement transformée.

Les neuf ajouts sont `app.agent.galaris_identity`,
`app.document.retire_goal_filing`, `app.document.retire_summary_history`,
`app.document.typed_sources`, `app.document.typed_documents`,
`app.document.typed_role_capabilities`, `app.goal.current_content`,
`app.skill.personal_learning` et `bridge.hermes.retire_agent_columns`.

Les retraits d'anciens mots-clés de révision et de `profile_legacy_source` sont des
choix explicites des décisions [0246](../decisions/0246-current-resource-summaries.md)
et [0248](../decisions/0248-agent-canonical-state.md), pas des champs oubliés par
le transfert. Ils rendent indispensable une sauvegarde coordonnée pour revenir
à l'ancienne version.

## Défauts reproduits et corrections

### 1. Dataset peuplé : destination absente avant l'expansion

**Défaut de 0.3.0 reproduit.** L'action `app.document.typed_sources`, exécutée en
`BEFORE_EXPAND`, insérait dans `documents.summary_generated` et lisait les nouveaux
champs de description de `datasets`. Ces colonnes n'existent pas en 0.2.0.
Un Dataset suffit à provoquer `UndefinedColumnError` avant l'expansion. Le même
scénario sans Dataset passe. Les tests existants avaient déjà conservé ces champs
du schéma cible dans leur reconstruction historique, ce qui masquait l'erreur.

**Correction locale :** l'archive seule est constituée et vérifiée avant expansion.
La copie et le classement attendent `AFTER_EXPAND`. Les FK changent toujours après
preuve du transfert. Les deux nouveaux checksums déclarent leur compatibilité
avec les actions inachevées de 0.3.0. Le test existant retire maintenant les vrais
ajouts absents de 0.2.0 et vérifie archive, interruption, reprise, contenu et ACL.
La contrainte transitoire « destination déjà copiée avant expansion » est retirée ;
sa garantie de conservation reste couverte par l'archive et les sources intactes.

### 2. Agent créé pendant une contraction différée

**Défaut reproduit.** Le runtime 0.3.0 ne renseigne plus `profile_media_type`, mais
la colonne conservée avait encore son défaut 0.2.0 `text/markdown`. Un nouveau
profil HTML était ainsi marqué Markdown, puis échappé à tort au prochain passage.

**Correction locale :** une préparation idempotente change uniquement le défaut
des futures lignes en `text/html` avant expansion. Le format des anciennes lignes
reste disponible pour leur conversion. Un scénario PostgreSQL conserve l'ancien
schéma, crée un agent avec le nouveau modèle, puis reprend et vérifie son HTML.

### 3. Goal créé ou modifié pendant une contraction différée

**Défaut reproduit.** L'ancienne FK `description_document_id` restait `NOT NULL`
alors que le nouveau runtime ne l'écrit plus. Une création pouvait échouer après
un démarrage déclaré utilisable. La postcondition comparait aussi indéfiniment
le Goal transféré à sa description retirée, bloquant une reprise après édition.

**Correction locale :** la FK source devient nullable avant expansion, sans
effacer les références existantes. Le transfert ignore les Goals créés directement
dans le nouveau format. Copie et retrait de la description source restent atomiques ;
les éditions légitimes ultérieures sont conservées. Les tests couvrent création,
édition, reprise et conservation complète des ressources de suivi.

### 4. Appartenance d'équipe révoquée puis rétablie par une reprise

**Défaut de droits reproduit.** Tant que `agents.group_id` subsiste, la postcondition
exigeait que l'appartenance historique reste présente dans `agent_teams`. Une
révocation légitime après l'import était donc annulée à la synchronisation suivante.
Le même problème concerne un import déjà terminé par un binaire publié.

**Correction locale :** références historiques et preuve de transfert atomique dans
`galaris_migration.agent_team_sources`. La preuve historique de réussite du journal
permet de reprendre les imports publiés sans restaurer leurs droits supprimés.
La source n'est plus comparée indéfiniment à l'appartenance courante. Le nouveau
checksum accepte explicitement l'ancien. Les tests couvrent premier import,
import publié déjà terminé, remise en attente, révocation et contraction réelle.

Le contrôle des 25 colonnes retirées ne trouve qu'une colonne `NOT NULL` sans
défaut : la FK Goal corrigée au point 3. Les autres colonnes sont nullables ou
possèdent un défaut ; le défaut de format Agent est le cas sémantiquement erroné
reproduit au point 2. Ce contrôle structurel ne remplace pas l'examen des transferts.

### 5. Diagnostic de la première panne masqué par une tentative ultérieure

Les anciens journaux hôte ne conservaient que les étapes. Le terminal affichait
seulement les 200 dernières lignes des services. Une nouvelle tentative recréait
le conteneur, tandis qu'une reprise pouvait remplacer `last_error`.

**Correction locale :** sortie de démarrage et logs backend complets de la tentative
dans le fichier d'update, masquage préalable des secrets, conservation de l'échec
initial en cas d'erreur de collecte. DbAdmin réaffiche toutes les causes conservées
des actions inachevées avant validation et avant toute nouvelle exécution.

Une action journalisée comme inachevée n'a pas forcément échoué : les obligations
sont enregistrées avant le DDL. L'échec Dataset peut donc laisser la conversion
Agent en `deferred` avec zéro tentative, puis provoquer son erreur de checksum
au retour vers 0.2.0. Le scénario ancien code 0.3.0 → refus par 0.2.0 → reprise par
le candidat est vérifié séparément. Cela explique un mécanisme compatible avec
les symptômes rapportés, sans établir la cause de l'installation extérieure.

## Refus de sécurité et limites qui restent explicites

- Un profil historique contenant des éléments interdits par le contrat HTML peut
  toujours bloquer sa conversion. Il n'est ni tronqué ni remplacé silencieusement.
  L'erreur indique maintenant l'agent, le champ, le format source et la cause.
- Un contenu source manquant, un conflit d'identité documentaire, des fichiers
  Skill divergents ou une archive endommagée ne peuvent pas être considérés comme
  une conversion réussie. Les sources et diagnostics doivent rester conservés.
- Un ancien binaire n'est pas une procédure de retour arrière après contraction.
  Le test de retour utilise une restauration coordonnée de la base, des fichiers,
  des clés et de l'ancien binaire.
- La comparaison porte sur les schémas attendus des tags. Elle ne mesure ni les
  écarts d'une base extérieure ni tous les volumes, contenus ou configurations
  PostgreSQL possibles. Une erreur diagnostiquée avec conservation des sources est
  préférable à une convergence obtenue en ignorant un transfert invalide.

## Preuves à conserver avant publication

Les exports et reproductions détaillés restent sous `artifacts/db-upgrade-audit/`.
La couverture durable est portée par `test_typed_document_upgrade.py`,
`test_column_retirement.py`, `test_content_upgrade.py`, `core/dbadmin/tests/test_actions.py`
et les tests shell d'update. Le canari de `make tests-upgrade` contient maintenant
un Dataset et sa révision, en plus du document Texte, de son historique, de ses
droits et de sa pièce jointe : un canari Texte seul ne détectait pas le défaut n° 1.

Vérifications effectuées sur le code local corrigé :

- Ancien binaire 0.2.0 réellement peuplé → candidat : convergence, contenu courant
  et révisions Texte/Données, ACL par API, seconde synchronisation et restauration
  coordonnée avec l'ancien binaire réussis (`full-upgrade.log`).
- Même parcours avec le binaire publié 0.3.0 : échec attendu et constaté sur
  `documents.summary_generated` avant expansion (`published-030-reproduction.log`).
- Reconstruction intégrale du schéma 0.2.0, cas vide/peuplé, refus de rétrogradation
  après l'échec publié puis reprise corrigée ; écritures Agent/Goal en contraction
  différée ; scénarios permanents de transfert et journalisation vérifiés.
- Suites connexes de séparation documentaire, préservation, résumés, apprentissage
  Skill et garanties opérateur : **33 tests réussis** (`related-migrations.log`).
- Tests de reprise documentaire : **3 réussis** (`document-recheck.log`) ;
  actions DbAdmin et conservation de toutes les causes avant refus : **16 réussis**
  (`action-recheck.log`). La série combinée des corrections Dataset/Agent/Goal,
  de leur reproduction et de la journalisation a réussi : **38 tests** (`final-tests.log`).
- La recherche de variantes a ensuite reproduit les deux cas de révocation d'équipe
  avant correction (`team-revocation-reproduction.log`) ; sa vérification est séparée
  dans `team-revocation-verification.log`.
- `make tests-update` et un backend Docker Compose réel en échec ont vérifié la
  collecte stdout/stderr au-delà de 350 lignes, le masquage et la conservation du
  code d'erreur initial. `make typecheck` a réussi.

La préparation d'une 0.3.1 doit distinguer ces vérifications ciblées de la
qualification du commit et des images réellement publiés. Cet audit ne remplace
ni les contrôles de publication, ni une validation complète demandée par l'utilisateur.
